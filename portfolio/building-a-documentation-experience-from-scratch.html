Building a Documentation Experience from Scratch

Creating the first centralized, task-focused documentation experience for a SaaS platform supporting online food pantry operations.

Role
Technical Writer & Documentation Designer
Focus
Content strategy, technical writing, information architecture, UX content
Tools
Confluence, custom in-app documentation portal

Overview

I created the first documentation system for a SaaS platform supporting online food pantry operations. The product served multiple audiences—including shoppers, pantry administrators, developers, and internal teams—but had no centralized user documentation.

My work included planning and writing help-center content, user guides, release notes, and external product documentation. I also built an in-app portal so users could access guidance within the product experience.

The challenge

The platform supported two very different primary audiences:

  • Shoppers needed clear, approachable guidance for creating accounts, joining food pantries, and placing orders.
  • Pantry administrators needed more detailed instructions for configuring services and managing day-to-day operations.

Without existing documentation, users and internal teams had no consistent source of truth. Product knowledge was distributed across the application, its codebase, individual developers, and conversations with clients.

The documentation therefore needed to do more than explain interface elements. It had to translate complex product behavior into task-focused guidance for people with different levels of technical knowledge.

My approach

Learning the product

Because no documentation foundation existed, I began by reconstructing how the product worked.

I reviewed the application and its code to understand system behavior, edge cases, and dependencies. I worked with other developers to confirm technical details, and spoke with clients to understand how the software fit into their actual workflows.

This combination helped me distinguish between how the product was designed to work, how it behaved in practice, and how users understood and described their tasks.

Designing the content structure

I organized the documentation around user goals rather than mirroring the product’s internal architecture.

For shoppers, that meant emphasizing common tasks and using direct, accessible language. Administrator content required more context, including prerequisites, configuration decisions, and the effects those decisions could have elsewhere in the system.

The planned documentation included:

  • Help-center articles
  • Task-based user guides
  • Release notes
  • External product documentation
  • Guidance embedded in an in-app portal

Treating documentation as part of the interface

I wanted users to be able to find help without leaving the product or understanding how the underlying system was organized. To support that goal, I built an in-app documentation portal in addition to maintaining content in Confluence.

This made the documentation effort both a writing project and a UX project. I considered navigation, labels, content hierarchy, discoverability, and how much information users needed at different points in their journey.

Maintaining accuracy

I validated content by comparing multiple sources: the application itself, the codebase, conversations with developers, and feedback from clients.

This was especially important when the visible interface did not fully communicate the business rules operating behind it. Rather than document assumptions, I traced behavior back to its source and worked with subject-matter experts to resolve inconsistencies.

Outcome

I established the structure and initial content for a documentation experience where none had previously existed.

I was reassigned before I could confirm the final launch or collect usage data, so I do not present this work as a measured adoption success. The project demonstrates my ability to:

  • Build a documentation strategy from a blank slate
  • Learn a complex product through code and stakeholder collaboration
  • Write for technical and nontechnical audiences
  • Organize information around user goals
  • Connect documentation decisions with the wider product experience
  • Design a sustainable foundation for future help content

Reflection

The project reinforced that documentation is not simply a record of product behavior. It is one of the ways users experience the product.

Effective documentation requires many of the same skills as UX design: understanding the audience, anticipating questions, reducing cognitive load, choosing the right terminology, and making information available at the moment it is needed.
